# 정상 전투에서 정리되지 않던 결과

같은 Room에서 전투를 반복하자 메모리가 계속 증가했습니다. 사용 중인 할당량도 함께 늘어 할당자 설정보다 살아 있는 객체의 보존 경로를 조사했습니다.

## 30초가 지나도 남은 이유

ClaimLoot가 현재 전투를 가리키면 현재 Battle이 처리했습니다. 만료 정리는 과거 Battle의 결과를 조회하는 경로에만 있었습니다. 정상적인 반복 전투는 그 경로를 지나지 않아 30초 보존 정책이 있어도 결과가 Room Cell의 수명 동안 쌓였습니다.

기존 만료 조건을 재사용해 새 결과 삽입 직전에 정리하도록 수정했습니다. 별도 타이머는 추가하지 않았습니다. 새 결과가 추가되지 않으면 정리가 지연될 수 있습니다.

[정리 함수와 호출 위치](code/memory-retention.txt)

## 진단 기록

| jemalloc 항목 | 당시 기록 |
| --- | ---: |
| 진단 규모 | 합성 세션 3,000개 |
| 실행 시간 | 30분 |
| stats.allocated 증가 | +246.3 kB/s |
| stats.resident 증가 | +255.3 kB/s |
| live 할당 증가 중 결과 보존 경로의 비중 | 98.7% |

위 두 기울기는 allocator 지표입니다. 프로세스 VmRSS와 섞지 않습니다. 98.7%는 수정 커밋의 힙 분석 기록에 있는 귀속 비율이며 메모리 감소율이 아닙니다. 이번 공개 작업에서 원본 heap stack을 다시 계산하지 않았습니다.

## 회귀 테스트

[retainedLootStaysBoundedAcrossBattles 발췌](code/memory-retention-test.txt)는 보존 창을 넘겨 전투를 두 차례 끝낸 뒤 결과 보존 깊이가 1인지 검사합니다. 당시 커밋은 정리 호출을 제거하면 이 검사가 실패했다고 기록합니다. 여기서 테스트를 새로 실행했다고 주장하지 않습니다.

수정 전 source는 `863849d4626b182d34da2e8bea505813ac0cc751`이고 수정 후는 `3e703cf7b0258804bdf110432db7449b9547a17c`입니다. 진단 브랜치의 수정이며 현재 제품 main에는 없습니다. main 기반 후속 브랜치 `407512f`에 같은 정리가 재적용됐지만 병합되지 않았고 새 부하 실행도 없습니다.

[수정본의 5,250세션 실행](capacity-5250.md)은 별도 실행으로 구분합니다.
